# Python server target: Django + Ariadne

Status: in progress, 2026-11-16.

## Goal

A `djangoAriadne` server config next to `fastapiAriadne`, sharing everything that is not the web framework. The developer
implements the same service Protocols; the project keeps its own Django settings and urls.

## Shape

Ariadne runs as a plain ASGI app, so the whole GraphQL side is framework independent: models, services, guards, loaders,
resolvers, context, `type_defs.py`, subscriptions and GraphQL uploads are generated by one shared serializer
(`PythonAriadneServerSerializer`). Only these differ per framework:

| | FastAPI | Django |
|---|---|---|
| GraphQL over HTTP | Ariadne's ASGI app, mounted on a `Route` | `runtime/graph_link_view.py`: an async Django view over `ariadne.graphql`, Django `HttpRequest` in the context |
| Subscriptions | the same ASGI app | `GraphLinkWebSocketRouter` in `create_app` (hands the WebSocket path to Ariadne, answers `lifespan`); Channels is the alternative |
| REST runtime | `rest/support.py`, `uploads.py`, `download.py` on Starlette | the same file names on Django (`HttpRequest`, `JsonResponse`, `request.read`, `parse_file_upload`, `StreamingHttpResponse`) |
| REST registration | `rest/router.py`: an `APIRouter` built from the route table | `rest/urls.py`: one CSRF-exempt `re_path` view per route, falling through to later routes that match |

Shared and generated once: the handlers and the route table (`rest/routes.py`, `build_rest_routes`), the framework-neutral
validation (`rest/core.py`), models, services, resolvers, loaders, guards. The REST serializer is abstract with a FastAPI and
a Django subclass that only name the request type, imports and runtime constants.

## Decisions (taken without the user, who has not used Django; revisit if wrong)

1. Async over ASGI, async services only, same Protocols as FastAPI. Sync Django would need a second flavor and Channels for subscriptions.
2. Plain Django views, not DRF: DRF serializers would fight the generated pydantic models.
3. Separate config key (`djangoAriadne`), shared base config `AriadneServerConfig`.
4. The integration service implementations move to `servers/python_impl/` and both servers wire them.

## Phases

1. Refactor: shared base config, serializer, REST serializer and constants. FastAPI suites stay green.
2. Django entry point, urls, adapter, generator branch.
3. `servers/python_django_server` (port 9972): faults, REST, GraphQL suites and the client harnesses.
4. Django upload server (GraphQL uploads share the ASGI path), CI, docs, tests.

## Known Django limits

- Django reads the whole body before the view runs (ASGI handler buffers to a temp file), so request bodies are not streamed to the service as they arrive.
- `django-cors-headers` is not needed: Starlette's CORS middleware wraps the whole ASGI app.

## Status

Done: all phases (redone Django-native: an earlier version adapted Django requests to Starlette and was dropped). Django server passes faults 49/49, REST 202/202, GraphQL 94/94, the upload suite 6/6 and the dart, ts, python and go clients.

The integration servers exist for GraphQL only, REST only and both (`servers/python_{fastapi,django}_{graphql,rest}_server`, ports 9923/9922/9921/9920), all driven by `servers/python_impl/run_*.py` with `GL_MODE`.
