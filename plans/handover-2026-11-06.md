### 3.1 Bug 1 (fixed) — why

`GLQueryDefinition.fragments()` took "fragments used directly + one level of each one's `dependecies`". Dependencies come from two
mechanisms: (A) `GLFragmentDefinitionBase.updateDepencies` follows spreads found in the fragment text transitively but cannot see
inside inline-fragment projections (their `getDependecies()` returns `{}`); (B) `updateFragmentAllTypesDependencies` /
`handleFragmentDepenecy` adds direct edges for inline fragments (interface to implementers, union to members) with `addDependecy`,
never expanded. So `feed` (uses `_all_fields_Entity`) lacked `_all_fields_Attachment`, and `article` lacked
`_all_fields_Photo/Video/Document`. Spring rejected both with `Undefined fragment`.

### 3.2 Bug 5 (open) — current understanding

Trigger: a custom query that selects some but not all fields of a type that has a cyclic edge. Example that corrupted the generated
Dart (`article.dart` replaced by a partial class, `Entity.fromJson` no longer compiled): `feed { __typename id createdBy ... on Article { title cover { ... on Photo { id url } } attachments { ...AttachmentParts } } ... on Comment { text } }`
against the integration schema.

Likely cause, read in `gl_grammar_projection_extension.dart`, `_isExhaustiveProjection(result, realType)` (around line 500):

- It returns `true` when every serializable field of the real type is either selected or "a cyclic edge" (`typeRequiresProjection(f.type) && isFieldCyclic(realType.token, f.type.inlineType.token)`).
- The comment says this is for depth-truncated all-fields views, so they earn the bare schema name (`Author`) and dedup against the full type.
- It cannot tell "the generator truncated this" from "the user left this field out". `Article.related: [Entity]` is cyclic
  (`Entity` includes `Article`), so omitting it counts as covered and the projection is named `Article`.
- Observed end to end with `fetchNode { node(id) { id ... on Entity { createdBy } ... on Article { title } } }` on the real schema
  (Article has six fields, the query selects three): `FetchNodeResponse.node` became `Entity?`, decoded with the full `Article.fromJson`,
  which throws `type 'Null' is not a subtype of type 'List<dynamic>'`. Something besides `related` is also treated as covered here
  (`cover` and `attachments` are not obviously cyclic): **check `isFieldCyclic` for unions/interfaces** before fixing.

Suggested next step: write the minimal failing IR test with a schema where a type has a cyclic edge and a non-cyclic field, select
a strict subset, and assert the projected type's name is not the declared name and its fields are the selected ones. Then decide how
to distinguish generator truncation from user omission (probably: only apply the cyclic exemption when the projection map comes from
an all-fields fragment).

### 3.3 Bug 7 (open) — current understanding

Seen with `attachment(id: $id) { ... on Photo { ...PhotoParts } ... on Video { id } }` (`fragment PhotoParts on Photo { id url width }`)
and with `node(id: $id) { id ... on Article { attachments { ...AttachmentParts } } }`. Both project to an abstract type with only `id`,
which the generator reuses as the schema's existing `SearchResult { id }` (this reuse is by design, `same_type_signature`).
`SearchResult.fromJson` switches on `__typename` and returns the projected class registered first for that member
(`Photo_IdWidth`, `Article_CoverIdTitle`), so another query's selection for the same member is lost or the decode throws.
Server side is correct. Suspect code: `addToProjectedTypes` / `findSimilarTo` / `_fillProjectedInterfaces` /
`fixProjectedInterfaceConflicts` (not read yet). Not yet reduced to an IR test.

### 3.4 Bug 8 (Swift) — facts

- Swift `fromJson` is non-throwing. `swift_serializer.dart`: `_dispatchFactory` default branch (~line 298) and `_discriminated` default
  branch (~line 323) emit `fatalError(...)`; required fields use `map["x"] as! T`.
- Consequence: XCTest dies with signal 5 and no assertion can be written for an unknown/absent/null discriminator or a missing field.
  That is why `PolymorphismNestedTests.swift` has only the happy-path and unknown-extra-keys cases.
- It applies to **GraphQL too** (any unknown `__typename`), by reading the generator; not run.
- Every other client throws a catchable error.
- The user agreed that throwing is the right behaviour. The plan is in `swift-throwing-polymorphic-decode.md`. Open questions there:
  one error type or two (`RestDecodeError` exists), throw vs unknown-member fallback, accept the breaking change to public `fromJson`,
  and whether the `as!` force casts follow in the same release.

### Gotchas hit this session

- **JUnit 5 silently skips a test method that returns a value.** Kotlin `fun x() = runBlocking { ... assertIs<..>(..) }` returns the asserted value and is
  skipped. Use `runBlocking<Unit>` and check the test count in `build/test-results` / surefire reports.
- macOS `sed -i` needs `sed -i ''`.
- `swift test` must have `DEVELOPER_DIR` set (XCTest is not in CommandLineTools).
- In Swift tests, `await` inside `XCTAssertEqual(...)` autoclosures does not compile: assign first.
- Kotlin/Java real GraphQL tests build clients through `Fixtures.newRealClient()`; Dart/TS through `real_server_adapter`.
- Go type switch on generic values: used a `kinds[T any]` helper; Go interface slices hold `nil` for null elements.
- The two GraphQL schemas (client `schema.gql` and Spring `schema.graphqls`) are separate files; the Spring one has no directives and no `counterTickRestart`.
- Stale generated files: when a custom query is removed, regenerate; the Dart generator does clean obsolete files, but check `lib/generated`.
- Spring's `ClassNameTypeResolver` needs record names equal to GraphQL type names.
