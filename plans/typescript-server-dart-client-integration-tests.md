# TypeScript Server + Dart Client Integration Tests

## Goal

Integration-test the generated Express+Apollo server (`plans/typescript-express-apollo-server.md`)
by generating a real backend, backing it with handwritten stub services, generating a Dart
client against the same schema, and running Dart tests against the running server. File
upload is out of scope for now.

## Status

- Express+Apollo server generator: implemented, manually tested, working.
- No automated tests yet for the TS server.
- `validateMappingFieldArguments()` experiment in `gl_grammar_service_extension.dart` was
  added then **reverted** — not part of this plan.

## Design (agreed)

- New folder: `integration_tests/typescript_server/`
  - `config.json` (mode: server, expressApollo) generating into `src/generated/`
  - `schema/schema.gql` — shared schema (see below)
  - `src/impl/*Service.ts` — **handwritten** stub services returning fixed fixture data
    (e.g. `getUser("1") -> { id: "1", name: "Ramdane" }`). Out of codegen scope, committed.
  - Runs on a fixed port (suggest **9997**, next free port after the existing 9999/9998
    Spring real-server ports).
  - `Makefile`: `generate`, `start-server` (background `tsx`, no actuator — use `lsof`/PID
    file like other non-Spring suites), `stop-server`, `test`, `ci`.

- New folder: `integration_tests/dart_client_tests_ts_server/` (or similar name)
  - Same shape as `dart_client_tests_real/`: `config.json` (mode: client) pointing at the
    **same schema**, `lib/generate.dart`, `test/*_test.dart`.
  - Tests hit `http://localhost:9997/graphql` and assert against the stub fixtures.
  - `Makefile`: `generate`, `test`, `ci` (start TS server, generate, test, stop TS server).

- Wire both into `integration_tests/Makefile` (new `typescript-server` / `ts-server-real`
  targets, included in `all-real`).

## Shared schema coverage

One schema (Author/Article domain) covering:

- Queries: nullable + non-nullable single object, list, query with args.
- Mutations: create/update/delete, object return + scalar return.
- Subscriptions: plain + with argument.
- Batch mapping: `Author.articles` (`@glSkipOnServer(batch: true)`, DataLoader).
- Non-batch schema mapping: `Article.author` (`@glSkipOnServer(batch: false)`).
- Field-with-arguments mapping: `Article.relatedArticles(limit: Int!)`
  (`@glSkipOnServer(batch: false)`) — exercises argument forwarding into the resolver.
- No `Upload` scalar / upload mutations.

## Required fix before mapping-with-args test can pass

`lib/src/serializers/express_apollo_server_serializer.dart`:

- `_serviceMappingMethod()` (~line 122) and `_writeTypeMappings()` (~line 360) currently
  ignore `mapping.field.arguments` for non-batch mappings. Need to:
  - Append `mapping.field.arguments` (typed) to the service interface method signature
    generated by `_serviceMappingMethod()` for non-batch mappings.
  - In `_writeTypeMappings()`, destructure the GraphQL field args from the resolver's
    second parameter and forward them into the service call
    (`$sVar.${m.key}(parent, args.limit, context, info)` style).
  - Scope: **non-batch mappings only**. Batch mappings + arguments remain unsupported for
    TS/Apollo (DataLoader batches by key; per-item args would need a composite cache key —
    out of scope here).

This fix lives in this plan's scope (it's required for the `relatedArticles` test case),
but is otherwise independent of the test-harness work above.

## Open questions / follow-ups (not blocking this plan)

- `jvm_spring_server_serializer_base.dart` `_validateFieldArguments()` throws on
  `batch: true` + arguments, but `java_spring_controller_serializer.dart` already emits
  `@BatchMapping` + `@Argument` for that case — looks like an existing inconsistency.
  Worth a follow-up plan to either relax the Spring validation or document why batch+args
  is disallowed there.
- Whether TS/Apollo should ever support batch+args via composite-key DataLoader is a
  possible future enhancement, not needed for this plan (the `relatedArticles` field is
  scoped to `batch: false`).
